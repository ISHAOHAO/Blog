> 本文参考了 [Web 安全学习笔记](https://websec.readthedocs.io/zh/latest/index.html) 的知识框架，并结合 OWASP 与 MDN 的一手资料重新整理。文中的测试只适用于自己拥有的程序、明确授权的测试环境或本地靶场；不要扫描、登录、修改或攻击任何没有得到授权的站点。

如果你刚接触 Web 安全，最容易遇到的困惑是：教程里同时出现 HTTP、Cookie、SQL、XSS、权限、JWT、SSRF 等词，好像每个词都很重要，却不知道它们之间是什么关系。

其实，Web 安全可以先用一句话理解：

> **让正确的人，在正确的时间，以正确的方式，访问正确的数据，并且让所有异常行为都能被限制、记录和追踪。**

这篇文章不追求把所有工具和漏洞 payload 罗列一遍，而是先建立一张“地图”：网站是怎样工作的，信任边界在哪里，常见漏洞为什么出现，以及开发者和测试者应该如何验证和修复。

## 一、你将从这篇文章学到什么

读完后，你应该能够：

- 看懂一次浏览器访问网站时发生的基本过程；
- 区分认证、授权、会话、Cookie、Token 和 CORS；
- 理解 SQL 注入、XSS、CSRF、SSRF、越权和文件上传风险的根因；
- 知道“过滤一下输入”为什么通常不够，以及更可靠的防御方式；
- 为自己的小项目列出一份基础安全检查清单；
- 在本地靶场中安全地练习，而不是把测试对象误认为互联网上的真实网站。

## 二、先理解：浏览器和服务器如何对话

### 1. 一次请求经过了什么

当你在浏览器地址栏输入 `https://example.com/profile` 时，可以把它简化成下面这条链路：

```text
浏览器
  │
  ├─ DNS：example.com 对应哪个 IP？
  ├─ TCP/QUIC：建立网络连接
  ├─ TLS：协商加密并验证证书
  └─ HTTP：发送请求并接收响应
          │
          ├─ 反向代理 / CDN
          ├─ Web 应用
          ├─ 数据库
          └─ 文件存储、缓存、消息队列等其他服务
```

HTTP 是 Web 的应用层协议。浏览器发送的是 request，服务器返回的是 response。一个请求通常包含方法、路径、请求头和请求体；一个响应通常包含状态码、响应头和响应体。

例如，下面是一个抽象的登录请求：

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/json

{"username":"alice","password":"用户输入的密码"}
```

服务器可能返回：

```http
HTTP/1.1 200 OK
Set-Cookie: __Host-session=随机会话标识; Path=/; Secure; HttpOnly; SameSite=Lax
Content-Type: application/json

{"ok":true}
```

这里有几个重要的安全问题：

- 密码是否只通过 HTTPS 传输？
- 服务端是否真的验证了密码，而不是相信浏览器传来的 `isAdmin` 字段？
- 会话 Cookie 是否设置了 `Secure`、`HttpOnly` 和合适的 `SameSite`？
- 登录失败时是否会暴露“用户不存在”还是“密码错误”等过多信息？
- 后端是否限制了登录尝试频率？

这些问题说明，安全不是页面上加一个按钮，而是贯穿请求、业务、存储和部署的完整过程。[MDN 的 HTTP 概览](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Overview) 对请求、响应和客户端—服务器模型有更完整的介绍。

### 2. 资产、威胁、漏洞和风险

初学者可以用四个词分析任何 Web 安全问题：

| 词语 | 含义 | 例子 |
| --- | --- | --- |
| 资产 | 需要保护的东西 | 用户资料、订单、密码重置链接、服务器凭据 |
| 威胁 | 可能造成伤害的行为或主体 | 恶意用户、被盗账号、自动化程序 |
| 漏洞 | 让威胁得以发生的弱点 | 缺少权限检查、拼接 SQL、任意 URL 请求 |
| 风险 | 漏洞发生后造成的可能损失 | 数据泄露、越权转账、服务器被接管 |

例如，“修改订单地址”是一个资产相关的业务操作；如果后端只根据 URL 里的订单编号查询，却没有检查订单属于当前用户，就形成了越权漏洞。漏洞不在于订单编号是数字，而在于服务端缺少“这个用户是否有权操作这个订单”的决策。

### 3. 三个安全目标：机密性、完整性、可用性

传统上常用 CIA 三元组描述安全目标：

- **机密性（Confidentiality）**：不该看到的人看不到，例如其他用户的地址和管理员密钥；
- **完整性（Integrity）**：不该修改的数据不能被修改，例如订单金额和权限角色；
- **可用性（Availability）**：服务能够正常提供，例如登录接口不能被无限次请求拖垮。

实际 Web 业务还经常关心身份真实性、可审计性和隐私。做安全分析时，不要只盯着“能不能拿到数据库”，也要关注能否冒充用户、修改业务数据、绕过流程或让服务无法使用。

## 三、零基础必须掌握的几个概念

### 1. 认证不等于授权

- **认证（Authentication）**：你是谁？例如密码、短信验证码、Passkey、OAuth 登录；
- **授权（Authorization）**：你能做什么？例如普通用户能查看自己的订单，管理员能审核退款；
- **会话（Session）**：服务器如何记住你已经登录？常见方式是 Cookie 携带一个随机会话标识。

“登录成功”只回答了身份问题，并不意味着用户可以访问所有资源。每个敏感操作都应该在服务端重新做授权判断：

```text
读取订单
  1. 从会话中得到当前用户 ID
  2. 从路径或请求体中得到订单 ID
  3. 查询订单，并确认订单属于当前用户或当前角色有权限访问
  4. 通过检查后才返回数据
```

把 `userId` 放在隐藏表单字段里、把 `role` 放在前端状态里、把“管理员按钮”在页面上隐藏，都不能代替服务端授权。浏览器里的 HTML、JavaScript、请求参数和响应都可以被用户查看或修改。

### 2. Cookie、Token 和 JWT 不是一回事

Cookie 是浏览器保存并自动发送的一种数据载体；Token 是应用定义的凭证；JWT 是一种规定了结构的 Token 格式。它们经常一起出现，但不能混为一谈。

JWT 通常由 header、payload、signature 三部分组成。签名可以帮助服务器验证内容是否被改过，但 JWT 的 payload 默认不是加密内容，因此不要把密码、私钥或不必要的敏感信息放进去。[Web 安全学习笔记的 JWT 章节](https://websec.readthedocs.io/zh/latest/auth/jwt.html) 可作为概念补充；真正实现时应优先使用框架和成熟库，并严格校验算法、签发者、受众和过期时间。

### 3. 同源策略和 CORS

浏览器用“源（origin）”区分网页之间的信任关系。源通常由协议、主机名和端口共同决定，例如：

```text
https://app.example.com:443
```

不同源之间的脚本访问会受到浏览器限制。CORS 是服务器通过响应头声明“哪些源可以读取我的响应”的机制，它不是登录系统，也不是服务端授权系统。

常见误区是把请求头中的 `Origin` 原样反射到 `Access-Control-Allow-Origin`。如果接口同时允许携带 Cookie，这可能让不可信站点读取敏感响应。应该使用明确的允许列表，并单独设计跨域接口的认证和授权。[MDN 的 CORS 指南](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/CORS) 介绍了浏览器对跨源请求的处理方式。

### 4. 客户端不可信，服务端才是安全边界

以下内容都不能直接当作事实：

- URL、查询参数、表单字段、JSON 请求体；
- Cookie、localStorage、JWT payload；
- 前端传来的 `isAdmin`、价格、折扣、用户 ID；
- 上传文件的扩展名、MIME 类型和文件名；
- HTTP 的 `Referer`、`User-Agent` 等可被伪造或缺失的请求头。

前端校验的主要价值是改善用户体验；安全校验必须在服务端完成。输入校验、输出编码、授权判断和业务规则都应在真正拥有数据访问权限的一侧执行。

## 四、五条贯穿始终的安全原则

### 原则一：先确定信任边界，再处理输入

把浏览器、第三方 API、文件上传、消息队列、数据库和内部服务都画在数据流图上，标出数据从哪里进入、经过哪些组件、最后影响什么资源。跨越信任边界时，要重新验证数据，而不是因为“它来自内部网络”就默认可信。

### 原则二：验证、规范化、编码是三件事

- **验证（validation）**：这个值是否符合业务允许的格式、长度和范围？
- **规范化（canonicalization）**：不同编码、路径或大小写写法是否被统一处理？
- **编码（encoding）**：把数据放入 HTML、JavaScript、URL、SQL 等不同语境时，是否使用了对应的安全 API？

“把特殊字符替换掉”不是通用防护。不同语境需要不同的处理方法；SQL 应使用参数化查询，HTML 输出应使用上下文相关的编码，路径应在规范化后检查是否仍位于允许目录内。

### 原则三：默认拒绝，按最小权限开放

权限系统应该默认拒绝，只有明确满足条件时才允许访问。数据库账号不应拥有应用不需要的管理权限；上传服务不应拥有执行代码的权限；应用服务器不应能随意访问所有内网服务。

### 原则四：使用分层防御，但不要把 WAF 当万能药

参数化查询、授权检查、Cookie 属性、CSP、网络隔离、速率限制、日志告警和备份，各自解决不同层面的问题。WAF 可以降低部分攻击噪声，但不能修复业务逻辑、越权和错误的服务器授权。

### 原则五：让安全规则可以被测试

安全要求要写成能验证的条件，例如“普通用户不能读取其他用户的订单”“上传文件不能在 Web 根目录执行”“登录失败必须限速”。只有能写成测试用例的规则，才容易在代码变更后持续保持。

## 五、常见 Web 漏洞：从根因理解防御

### 1. 越权和失效的访问控制

这是最值得优先学习的一类问题。它不一定有复杂 payload，常常只需要修改一个对象编号、HTTP 方法或接口路径。

典型场景：

```text
GET /api/orders/1001   ← 当前用户自己的订单
GET /api/orders/1002   ← 如果也能返回，就需要检查是否越权
```

服务端不能只检查“用户已经登录”，还要检查“当前用户是否拥有这个订单”。管理员接口同样需要明确的角色、资源和操作判断。对于 `GET`、`POST`、`PUT`、`PATCH`、`DELETE` 等每种方法，都要验证对应权限，不能因为页面没有按钮就认为接口安全。

防御重点：

- 在服务端集中执行授权决策；
- 使用“默认拒绝”和最小权限；
- 对对象级、功能级和字段级权限分别测试；
- 对同一接口分别使用未登录用户、普通用户和管理员测试；
- 不要信任前端隐藏字段、URL 中的角色或客户端计算出的价格。

OWASP Top 10:2025 仍把 Broken Access Control 放在第一位，建议把它作为任何 Web 项目的首要检查项。

### 2. SQL 注入：把数据误当成了代码

SQL 注入的根因不是“用户输入很坏”，而是应用把数据拼接进 SQL 语句，导致数据库无法区分“程序结构”和“用户值”。

不安全的思路是：

```js
// 不要把外部输入直接拼进 SQL 字符串
const sql = "SELECT * FROM users WHERE name = '" + username + "'";
```

更可靠的方式是参数化查询：

```js
const sql = "SELECT * FROM users WHERE name = ?";
const rows = await db.query(sql, [username]);
```

参数化查询让数据库把 `username` 当作值，而不是 SQL 语法的一部分。不要试图用黑名单过滤几个字符来代替参数化；动态表名、排序字段和列名如果确实需要动态生成，应使用服务端固定的允许列表。详细原则可参考 [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)。

测试时不要在陌生站点尝试注入语句。你可以在本地练习“输入不同内容时，程序是否始终使用参数化查询”，并通过代码审计、单元测试和日志确认实际执行路径。

### 3. XSS：把不可信内容当成了网页代码

跨站脚本攻击（XSS）的核心是：攻击者控制的内容最终被浏览器当作 HTML、JavaScript 或其他可执行语境解析。

常见分类包括：

- **反射型 XSS**：输入在当前响应中立即反射；
- **存储型 XSS**：输入被保存，之后展示给其他用户；
- **DOM 型 XSS**：前端 JavaScript 从 URL、存储等位置读取数据，并写入危险 DOM 接口。

一个危险的前端写法是：

```js
element.innerHTML = userInput;
```

如果只是展示文本，应优先使用：

```js
element.textContent = userInput;
```

如果业务确实允许用户发布格式化内容，则需要使用成熟的 HTML 清理库、严格限制允许的标签和属性，并结合内容安全策略（CSP）。不要只依赖 CSP，也不要把所有输入统一编码后就认为安全：HTML、属性、JavaScript、CSS 和 URL 语境的编码规则不同。[OWASP XSS 防御备忘单](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) 对这些语境有详细区分。

Cookie 设置 `HttpOnly` 可以减少脚本直接读取会话 Cookie 的机会，但它不能修复 XSS 本身，也不能阻止 XSS 代表用户发起操作；根本防护仍然是安全输出和安全 DOM API。

### 4. CSRF：浏览器带着你的身份发出了请求

跨站请求伪造（CSRF）利用的是浏览器自动携带 Cookie 的特性。假设用户已登录某个网站，另一个恶意页面诱导浏览器向该网站发送“修改邮箱”或“转账”的请求，如果服务端只凭 Cookie 认定请求可信，就可能执行不该执行的操作。

CSRF 与 XSS 的区别可以这样记：

- XSS 重点是“恶意脚本进入了目标站点的页面并执行”；
- CSRF 重点是“伪造一个来自已登录用户的请求”。

基础防御：

- 对会改变状态的请求使用 CSRF Token，并在服务端验证；
- 设置合适的 `SameSite` Cookie 属性；
- 对敏感请求校验 `Origin`，必要时检查 `Referer`；
- 不要用 GET 执行修改、删除、转账等有副作用的操作；
- 对高风险操作要求重新认证或二次确认；
- 不要把“接口是 POST”误认为已经防住 CSRF。

CSRF Token、SameSite 和 Origin 校验应结合应用架构选择，而不是复制一段固定代码。[OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) 和参考文档的 [CSRF 章节](https://websec.readthedocs.io/zh/latest/vuln/csrf.html) 都值得阅读。

### 5. SSRF：让服务器替攻击者访问资源

服务端请求伪造（SSRF）通常出现在“输入一个 URL，服务器帮你抓取内容”的功能中，例如图片导入、网页预览、Webhook、PDF 生成和 URL 检测。

风险在于：服务器可能比外部用户更接近内网，能够访问管理面板、云环境元数据、内部 API 或本机服务。攻击者并不一定需要直接进入内网，只要能影响服务器请求的目标，就可能借服务器的网络位置扩大访问范围。

安全设计应尽量避免“任意 URL 抓取”。如果业务必须请求远端地址：

- 只允许 `https` 等明确需要的协议，拒绝文件、脚本和其他不必要的协议；
- 对主机名使用允许列表，而不是只靠几个字符串黑名单；
- DNS 解析后检查 IP，拒绝回环、链路本地、私有网段和其他不应访问的地址；
- 正确处理重定向，并对每次跳转重新校验；
- 限制端口、响应大小、连接时间和重试次数；
- 将抓取服务放在隔离网络中，并使用最小网络权限；
- 不把内部响应原样返回给用户。

复杂场景还要考虑 DNS 重绑定、IPv6 和解析差异，因此“正则匹配 URL”通常不够。[OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) 提供了更完整的防御思路。参考文档中的 [SSRF 章节](https://websec.readthedocs.io/zh/latest/vuln/ssrf.html) 可用于了解风险范围，但其中的利用部分不应在未授权环境尝试。

### 6. 文件上传、路径穿越和命令注入

这三类问题经常一起出现在“服务端把外部输入交给文件系统或操作系统”的功能里。

#### 文件上传

不要只检查文件名后缀。更稳妥的做法包括：

- 限制大小、数量和上传频率；
- 使用业务允许列表，而不是“不是黑名单后缀就放行”；
- 在服务端检查文件内容与实际类型；
- 使用随机文件名，不保留用户原始文件名作为路径；
- 将文件放在不能直接执行脚本的存储位置，最好不在 Web 根目录；
- 图片需要重新解码、转换或清理元数据时，要考虑解析器风险；
- 下载时设置正确的 `Content-Type` 和 `Content-Disposition`。

#### 路径穿越

当用户可以指定文件名、模板名或下载路径时，不要直接把字符串拼接到文件系统路径。应先规范化路径，再确认最终路径仍位于预期根目录下，并使用允许列表映射业务 ID 到真实文件，而不是让用户提交任意路径。

#### 命令注入

如果功能可以调用系统命令，优先使用不经过 Shell 的库接口；参数采用固定的参数数组和严格允许列表。不要把用户输入拼进 `sh -c`、批处理文件或 PowerShell 字符串。即使输入看起来只允许数字，也要在服务端再次验证长度、范围和格式。

### 7. 安全配置错误、依赖和敏感信息泄露

有些漏洞不是代码写错，而是部署时留下了不必要的入口：

- 默认账号和默认密码没有更换；
- 生产环境开启调试页面或返回堆栈信息；
- 管理接口暴露到公网且没有额外保护；
- 数据库、对象存储或备份文件公开可读；
- 依赖长期不更新，或安装了来源不明的包；
- API 密钥、Cookie、密码出现在仓库、日志、截图和错误页面中；
- CORS、反向代理、TLS 或安全响应头配置过于宽松。

防御不是“上线前改一次配置”就结束，而是要把安全配置写进可重复的部署流程，并在 CI 中检查密钥、依赖、容器镜像、权限和公开文件。错误信息应对用户保持克制，同时把必要的诊断信息写入受访问控制保护的日志系统。

## 六、账号、密码和会话应该怎样设计

### 1. 密码不能用可逆加密或普通哈希保存

密码数据库泄露后，攻击者可以离线猜测密码。因此密码应使用专门的慢速密码哈希算法和唯一盐值，例如 Argon2id、bcrypt 或 scrypt，具体参数应按官方建议和服务器性能评估。不要使用 MD5、SHA-1 或“加盐后快速 SHA-256”来代替密码哈希。

应用还应：

- 只通过 HTTPS 传输密码；
- 设置合理的长度和常见密码拦截策略；
- 登录、注册、找回密码接口限速；
- 找回密码链接使用一次性、短时有效的随机令牌；
- 登录错误信息尽量统一，避免暴露账号是否存在；
- 对高风险操作要求重新认证或多因素认证。

可以参考 [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) 和 [Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

### 2. 会话 Cookie 的基础安全属性

一个常见的会话 Cookie 形态是：

```http
Set-Cookie: __Host-session=随机值; Path=/; Secure; HttpOnly; SameSite=Lax
```

这些属性的作用大致是：

- `Secure`：只通过 HTTPS 发送；
- `HttpOnly`：禁止普通 JavaScript 直接读取；
- `SameSite=Lax` 或 `Strict`：限制跨站请求携带 Cookie；
- `__Host-` 前缀：在支持的浏览器中要求 Secure、禁止 Domain 并固定 Path，有助于缩小 Cookie 作用范围。

具体取值要结合登录流程、跨站跳转和嵌入场景决定。[MDN Cookie 安全实践](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/Cookies) 解释了这些属性的行为。

登录成功后应刷新会话标识，退出登录、修改密码、权限变化和风险事件发生后应使旧会话失效。不要在 URL、日志或错误页面中暴露会话标识。

### 3. JWT 的几个常见误解

- JWT 的签名不等于加密，payload 默认可以被读取；
- JWT 不是越长越安全，也不是所有场景都比服务端 Session 好；
- 只解码 JWT 而不验证签名、算法、过期时间、签发者和受众是不安全的；
- JWT 一旦签发，撤销和轮换往往比服务端会话更复杂；
- 不能把用户提交的角色字段直接当作授权结论。

如果应用并不需要跨多个独立服务传递声明，服务端会话加安全 Cookie 往往更容易撤销和审计。

## 七、HTTPS 和安全响应头

### 1. HTTPS 解决什么问题

HTTPS 使用 TLS 保护传输中的机密性和完整性，并通过证书帮助客户端验证服务器身份。它不能修复越权、SQL 注入或业务逻辑错误，但没有 HTTPS 时，密码、Cookie 和页面内容可能在传输途中被窃取或篡改。

生产环境应：

- 全站使用 HTTPS；
- 正确配置证书链和自动续期；
- 将 HTTP 重定向到 HTTPS；
- 对登录和敏感接口禁止明文访问；
- 评估启用 HSTS，避免浏览器反复使用 HTTP。

### 2. 常见安全响应头

响应头不能代替代码修复，但可以减少浏览器侧风险：

| 响应头 | 主要目的 |
| --- | --- |
| `Content-Security-Policy` | 限制脚本、样式、图片等资源来源，降低部分 XSS 影响 |
| `Strict-Transport-Security` | 告诉浏览器后续优先使用 HTTPS |
| `X-Content-Type-Options: nosniff` | 避免浏览器对内容类型进行不必要的猜测 |
| `Referrer-Policy` | 控制 Referer 中泄露的路径信息 |
| `frame-ancestors` 或 `X-Frame-Options` | 限制页面被其他站点嵌入，降低点击劫持风险 |
| 合理的 CORS 头 | 只允许明确需要的跨源读取 |

配置 CSP 时建议先在报告模式观察违规情况，再逐步收紧；不要为了“让页面不报错”而使用过于宽松的通配符和 `unsafe-inline`。

## 八、把安全放进开发流程

安全最好在设计阶段介入，而不是上线后才做一次扫描。

### 1. 设计阶段：画数据流和威胁模型

至少回答：

- 哪些数据是敏感资产？
- 谁可以读取、创建、修改和删除它们？
- 哪些输入来自浏览器、第三方或上传文件？
- 应用是否会访问内网、执行命令或解析复杂文件？
- 哪些操作需要二次确认、限速或重新认证？
- 失败后如何记录、告警和恢复？

### 2. 编码阶段：优先使用安全抽象

- 使用框架默认的模板转义和成熟认证组件；
- 使用 ORM 的参数化接口，但不要因为使用 ORM 就跳过授权检查；
- 对输出选择正确的安全 API；
- 对敏感配置使用密钥管理或受保护的环境注入；
- 不要复制来源不明的安全代码片段，尤其是密码学和 Token 验证代码。

### 3. 测试阶段：按身份和状态覆盖

测试不只看“页面能不能打开”，还要覆盖：

- 未登录、普通用户、同组织用户、管理员和已禁用账号；
- 正常输入、空值、超长值、错误类型和边界值；
- 重放请求、重复提交、并发操作和过期会话；
- 直接访问接口、修改对象 ID、改变 HTTP 方法；
- 上传超大文件、错误类型文件和重复文件名；
- 第三方服务不可用、超时、重定向和返回异常数据。

OWASP 的 [Web Security Testing Guide](https://wstg.owasp.org/stable/2-Introduction/) 提供了从信息收集、身份管理、认证、授权、会话、输入验证到业务逻辑测试的系统框架。测试指南中的方法应只用于已授权的目标。

### 4. 上线后：日志、告警和响应

安全日志应记录足够的事件上下文，例如时间、请求 ID、用户或服务身份、资源、结果和失败原因，但不要记录密码、完整 Token、Cookie 或不必要的个人数据。

还要提前准备：

- 密钥泄露时如何撤销和轮换；
- 发现越权或数据泄露后如何隔离影响；
- 如何保留证据并通知相关人员；
- 如何修复、回归测试并确认漏洞没有再次出现；
- 备份是否可恢复，恢复过程是否经过演练。

## 九、适合小白的安全学习路线

不要一上来就背工具命令。推荐按下面的顺序学习：

### 第 1 阶段：补齐 Web 基础

掌握 HTML、CSS、JavaScript、浏览器开发者工具、HTTP 方法与状态码、Cookie、JSON、DNS 和基本 Linux 命令。能看懂一次请求和响应，比记住几十个工具参数更重要。

### 第 2 阶段：做一个故意简单的本地项目

用自己熟悉的语言做一个最小应用，包含注册、登录、个人资料、订单或留言功能，然后主动检查：

- 是否真的区分认证和授权；
- 是否对数据库使用参数化查询；
- 是否安全输出用户内容；
- 是否保护修改操作免受 CSRF；
- 是否限制登录、上传和资源访问频率；
- 是否把错误堆栈、密钥和会话写进日志或响应。

### 第 3 阶段：使用合法靶场

选择本地运行、明确用于训练的靶场，例如 OWASP Juice Shop、WebGoat 或其他教学环境。练习时先写下“漏洞根因—影响—修复—回归验证”，再使用工具观察请求变化。不要把真实公司的域名、学校网站、公共 IP 或随机互联网服务当作练习对象。

### 第 4 阶段：从漏洞转向防御

学习 OWASP Top 10、OWASP ASVS、Cheat Sheet Series 和 Web Security Testing Guide。每学一个漏洞，都回答四个问题：

1. 哪个输入跨过了哪条信任边界？
2. 应用为什么把数据当成了代码、权限或地址？
3. 最小可靠修复是什么？
4. 如何写一个回归测试证明它仍然安全？

### 第 5 阶段：进入真实项目的安全工程

进一步学习依赖和供应链安全、容器与云权限、密钥管理、日志告警、威胁建模、代码审计和事件响应。此时再学习代理、扫描器和模糊测试工具，才能知道工具结果代表什么，也知道哪些结果需要人工确认。

## 十、上线前快速检查清单

### 身份与权限

- [ ] 每个敏感接口都在服务端验证身份和资源权限；
- [ ] 普通用户不能通过修改 ID、路径或 HTTP 方法访问他人资源；
- [ ] 默认拒绝，管理员权限和服务账号权限都经过最小化；
- [ ] 登录、找回密码和高风险操作有速率限制或重新认证。

### 输入与输出

- [ ] 数据库查询使用参数化接口；
- [ ] HTML、属性、URL、JavaScript 等语境使用对应安全 API；
- [ ] 上传文件大小、类型、名称、保存位置和执行权限都有约束；
- [ ] 文件路径经过规范化，并确认没有离开允许目录；
- [ ] 不把不可信输入直接交给 Shell、模板引擎或反序列化器。

### 会话与传输

- [ ] 全站和敏感接口使用 HTTPS；
- [ ] 会话 Cookie 设置 `Secure`、`HttpOnly` 和合适的 `SameSite`；
- [ ] 登录、退出、改密和权限变化会刷新或撤销会话；
- [ ] Token 不出现在 URL、日志和错误页面中；
- [ ] JWT 按算法、签名、过期时间、签发者和受众完整验证。

### 部署与运营

- [ ] 生产环境关闭调试和详细堆栈；
- [ ] 没有默认账号、公开备份、仓库密钥和不必要的管理端口；
- [ ] 依赖、容器镜像和基础系统有更新与回滚策略；
- [ ] 对认证失败、越权、异常上传和服务端请求失败有日志与告警；
- [ ] 备份、密钥轮换和事件响应流程经过演练。

## 十一、最后记住三件事

第一，Web 安全不是“会不会使用某个工具”，而是能不能准确理解数据、身份、权限和信任边界。

第二，漏洞名称不是修复方案。看到 SQL 注入，要想到参数化查询；看到 XSS，要想到上下文相关输出编码和安全 DOM API；看到 CSRF，要想到状态变更保护；看到 SSRF，要想到协议、解析结果、重定向和网络出口的共同约束；看到越权，要想到服务端资源级授权。

第三，所有测试都应在授权范围内进行。好的安全学习既要理解攻击者如何发现问题，也要知道如何降低影响、修复根因、验证修复并保护真实用户。
