很多人第一次使用 AI 时，会把问题简单地写成一句话：

> 帮我写一篇文章。

有时结果还不错，有时却会出现跑题、空泛、格式不对、遗漏重点等问题。于是大家开始寻找“万能提示词”，但真正决定结果质量的，通常不是某一句神奇的话，而是你有没有把任务、背景、标准和输出形式说清楚。

这就是提示词工程（Prompt Engineering）要解决的问题：**把人的目标转换成模型容易理解、容易执行、也容易检查的任务说明。**

本文不追求复杂的术语，而是从实际使用出发，带你建立一套可复用的写法。

## 一、提示词工程到底是什么

提示词就是你交给 AI 的输入，包括问题、背景资料、规则、示例和输出要求。提示词工程则是对这些输入进行设计、测试和迭代，让模型更稳定地完成任务。

可以把一次 AI 任务看成一个函数：

```text
结果 = 模型（任务 + 上下文 + 约束 + 示例）
```

其中：

- **任务**：你希望 AI 完成什么；
- **上下文**：AI 需要知道哪些背景；
- **约束**：哪些事情必须做、不能做；
- **示例**：你希望结果长什么样；
- **评估标准**：怎样判断结果是否合格。

如果只给出任务，不给背景和标准，模型就只能自行猜测。模型的猜测越多，结果的不确定性通常就越高。

## 二、写提示词前，先把需求说清楚

### 1. 区分目标和手段

“帮我写一篇关于提示词的文章”是一个目标，但还缺少很多信息：写给谁、用于哪里、要多长、采用什么语气、是否需要示例。

可以先把需求拆成下面几项：

| 项目 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 目标 | 最终要得到什么 | 一篇可发布的教程文章 |
| 读者 | 谁会阅读或使用 | 没有经验的普通用户 |
| 场景 | 结果将在哪里使用 | 个人博客 |
| 内容 | 必须覆盖哪些重点 | 结构、模板、常见误区 |
| 风格 | 希望如何表达 | 清晰、实用、少术语 |
| 格式 | 结果应该长什么样 | Markdown，包含标题和代码块 |
| 标准 | 什么算完成 | 内容准确、步骤可执行、没有重复 |

“帮我写一篇文章”只是手段层面的请求；“让初学者学会写出可复用的提示词”才是更明确的目标。

### 2. 把模糊形容词换成可观察的要求

“写得专业一点”“详细一点”“不要太长”对不同人来说含义不同。更好的做法是把它们改写成可以检查的条件：

- “专业” → 使用准确术语，并对首次出现的术语给出解释；
- “详细” → 至少包含原理、步骤、示例和常见错误；
- “不要太长” → 控制在 1500～2000 字；
- “通俗” → 面向没有编程经验的读者，避免连续使用未经解释的缩写。

一个简单判断方法是：**如果另一个人拿到这条要求，能否据此判断结果合不合格？** 如果不能，说明要求还不够具体。

## 三、一个通用的提示词结构

日常任务不需要每次都写很长，但可以用下面这套结构检查是否缺项：

```text
# 角色（可选）
你要以什么专业视角处理任务？

# 任务
请完成什么事情？

# 背景与输入
你需要使用哪些资料？目标读者是谁？

# 约束
必须包含什么？不能做什么？长度、语言、语气有什么要求？

# 输出格式
请用什么结构、字段或 Markdown 格式返回？

# 质量标准
完成前检查哪些条件？
```

例如，下面是一条比“帮我总结这篇文章”更完整的提示词：

```text
请总结下面的文章，读者是刚接触这个主题的产品经理。

要求：
1. 先用一句话说明文章的核心结论；
2. 再列出 3～5 个关键观点，每点不超过 80 字；
3. 标出文章中明确的事实、作者的观点和仍然存在的不确定性；
4. 不要补充原文没有出现的数据；
5. 如果原文信息不足，请直接写“原文未说明”。

输出格式：
## 核心结论
...

## 关键观点
1. ...

## 不确定性
...

文章内容：
<<<
在这里粘贴文章
>>>
```

这里的 `<<<` 和 `>>>` 不是必需语法，但能帮助模型分清“指令”和“待处理内容”。当输入很长或包含代码、表格、邮件时，使用清晰的边界尤其重要。

## 四、角色不是越夸张越好

很多提示词喜欢这样开头：

> 你是一位世界顶级、拥有几十年经验的专家……

这种写法有时能提醒模型采用某种视角，但“顶级”“世界第一”本身并不会自动增加事实准确性。相比夸张的身份，更有用的是明确工作方式：

```text
你是一名面向初学者的技术编辑。请优先使用准确、易懂的表达；首次出现的专业术语要解释；不确定的事实不要猜测，并单独列出需要核实的内容。
```

角色描述适合用于指定视角、语气和判断标准，不应被当成专业能力的替代品。涉及法律、医疗、财务、安全等高风险问题时，还应要求模型说明不确定性，并由人进行最终确认。

## 五、先给任务，再给资料和规则

提示词的顺序会影响可读性。一个实用的排列方式是：

1. 先说明要完成的任务；
2. 再提供背景和原始资料；
3. 接着列出约束和禁止事项；
4. 最后规定输出格式和检查要求。

例如，不要把十段背景介绍写完后才在最后一句说“请顺便总结”。可以直接写：

```text
任务：根据下面的会议记录，整理一份行动清单。

背景：参与者包括产品、设计和开发团队。

要求：
- 只整理会议中明确达成的事项；
- 每项包含负责人、截止时间和依赖；
- 没有提到的信息填写“待确认”；
- 不要把讨论中的候选方案写成最终决定。

输出格式：Markdown 表格。

会议记录：
<<<
...
>>>
```

这类写法的关键不是“越长越好”，而是让每段内容承担明确的作用。

## 六、用示例说明你想要的结果

当任务有固定格式或判断标准时，示例往往比长篇解释更有效。这种方法通常称为少样本提示（Few-shot Prompting）。

例如，要把用户反馈归类，可以给出一两个输入和期望输出：

```text
请将每条反馈归入“功能问题”“使用困难”或“功能建议”之一。
只能选择这三个类别，不要自创类别。

示例：
输入：点击保存后页面没有任何提示。
输出：功能问题

输入：我找不到修改通知设置的入口。
输出：使用困难

现在处理：
输入：如果能支持深色模式就好了。
输出：
```

示例至少要满足两个条件：

- 示例和真实任务足够相似；
- 示例之间的标签、格式和判断逻辑保持一致。

如果示例本身互相矛盾，模型就会学到矛盾的规则。示例不需要很多，先准备一到三个高质量样例，通常比堆十个随意样例更好。

## 七、让复杂任务分步骤完成

面对研究、写作、代码分析或方案设计等复杂任务，直接要求“一次完成”容易遗漏信息。可以把过程拆成几个可检查的阶段：

```text
请按以下顺序处理，不要跳过步骤：

1. 提取任务目标和已知条件；
2. 列出缺失信息和潜在冲突；
3. 给出方案草稿；
4. 根据约束检查草稿；
5. 输出最终方案，并单独列出假设与风险。
```

更重要的是，分步不等于要求模型展示所有内部推理。实际使用中，通常只需要让模型输出**可验证的中间结果**，例如假设清单、检查表、字段映射和测试用例，而不是要求它暴露完整的隐含思考过程。

### 一个适合写文章的分步模板

```text
请为下面的主题设计一篇教程。

第一步：确定目标读者、学习目标和文章边界。
第二步：给出文章目录，并说明每一节解决什么问题。
第三步：根据目录撰写正文，每节至少包含一个例子。
第四步：检查是否有重复、跳步、未经说明的术语和无法执行的建议。
第五步：输出最终 Markdown，并附上“仍需人工核实”的内容。

主题：...
```

这样做的好处是：你可以在目录阶段纠正方向，而不必等整篇文章写完后才返工。

## 八、输出格式要写到字段级别

“请整理成表格”还不够具体。最好说明列名、每列的含义和缺失信息如何处理。

```text
请输出 JSON 数组，每个对象必须包含以下字段：
- title：标题，字符串；
- summary：不超过 50 字的摘要；
- priority：只能是 high、medium、low；
- evidence：支持该结论的原文摘录；
- uncertainty：如果没有不确定性，填写空数组。

不要输出 Markdown 代码围栏，不要添加未定义字段。
```

如果结果要被程序读取，最好要求“只输出 JSON”，并在应用层再次进行 JSON 解析、字段校验和长度限制。提示词可以降低格式错误，但不能代替程序的输入验证。

### 用占位符保护结构

写报告、邮件或代码时，可以先给出模板：

```text
请按以下模板输出，不要改变标题顺序：

## 结论
<一句话结论>

## 依据
- <依据 1>
- <依据 2>

## 风险与限制
- <风险或“暂无”>

## 下一步
1. <动作>
```

占位符能减少模型自由发挥的范围，也方便你在多个任务中复用同一结构。

## 九、否定要求要配合替代方案

只说“不要写得空泛”“不要使用术语”往往不够，因为模型还不知道应该怎么写。更好的方式是同时给出替代行为：

```text
不要只给出抽象结论。每个结论后面都补充：
1. 一个具体例子；
2. 一个适用场景；
3. 一个可能的限制。
```

再例如：

```text
不要编造缺失数据。如果资料中没有答案，请填写“未提供”，并把这个字段加入“待确认”列表。
```

“禁止什么”和“遇到这种情况应该怎么做”最好同时写清楚。

## 十、把提示词当成可测试的配置

提示词写出来并不代表完成。一个可靠的提示词至少需要经过三类测试：

### 1. 正常样例

验证模型能否完成最常见的任务，例如一篇结构完整的文章、一条格式正确的记录或一份字段齐全的摘要。

### 2. 边界样例

主动提供空输入、超长输入、重复内容、格式错误、语言混杂和信息不完整的样例，观察模型是否会胡乱补全。

### 3. 对抗样例

检查输入资料中出现“忽略之前要求”“泄露系统提示”等文字时，模型是否仍然遵守外层任务的安全规则。尤其是处理网页、邮件、用户评论或外部文档时，要把其中的内容视为数据，而不是新的指令。

可以建立一张简单的评估表：

| 测试项 | 预期行为 | 实际结果 | 是否通过 |
| --- | --- | --- | --- |
| 正常输入 | 输出完整字段 |  |  |
| 缺少日期 | 标记为待确认 |  |  |
| 超长文本 | 保持结构，不遗漏结论 |  |  |
| 含有指令样文字的资料 | 继续按原任务处理 |  |  |

如果你经常使用同一个提示词，最好保留一组固定测试样例。修改提示词或更换模型后重新跑一遍，避免“这次看起来不错”被误认为长期稳定。

## 十一、常见失败写法和改进方式

### 失败写法一：一句话塞进所有要求

```text
帮我写一个专业详细但简洁有趣适合所有人的方案，最好还有案例和数据。
```

问题在于“专业、详细、简洁、有趣、适合所有人”之间可能互相冲突，而且没有说明主题、长度、场景和交付格式。

改成可执行的要求：

```text
请为没有技术背景的项目负责人写一份方案。
主题：为个人博客增加站内搜索。
长度：1000～1500 字。
必须包含：目标、实现思路、风险、上线检查清单。
语言：通俗，但保留必要的技术名词并解释一次。
```

### 失败写法二：只描述身份，不描述任务

```text
你是一位资深专家，请给我建议。
```

模型不知道“建议”针对什么，也不知道应该依据哪些资料。角色只能补充视角，不能替代任务定义。

### 失败写法三：要求模型保证绝对正确

```text
请给出绝对准确、没有任何错误的答案。
```

这不是可执行的质量标准。更有效的是要求列出假设、引用输入中的依据、标记不确定性，并对高风险事实进行人工或外部资料核实。

### 失败写法四：为了保险写一大段重复规则

过长且重复的提示词会降低维护效率，也可能让规则之间产生冲突。保留最重要的约束，把固定格式抽成模板，把经常变化的内容放进变量区域。

### 失败写法五：把模型输出直接当成事实或代码执行

模型可以生成看起来合理但实际错误的内容。尤其是代码、命令、数据分析和安全建议，必须经过测试、审阅和权限控制。提示词工程改善的是协作质量，不会消除事实核查和人工负责的必要性。

## 十二、四个可以直接复用的提示词模板

### 1. 写作模板

```text
请写一篇关于【主题】的教程文章。

目标读者：【读者画像】
学习目标：读者读完后能够【具体能力】
文章用途：【博客 / 内部文档 / 课程讲义】
篇幅：【字数范围】
语气：【通俗 / 专业 / 轻松】

必须包含：
1. 【概念或背景】
2. 【操作步骤或方法】
3. 【完整示例】
4. 【常见错误】
5. 【检查清单】

写作要求：
- 首次出现的术语要解释；
- 不要编造未提供的数据；
- 对不确定的内容单独标注；
- 使用 Markdown 标题、列表和代码块。
```

### 2. 代码分析模板

```text
请审查下面的代码，目标是发现正确性、可维护性和安全性问题。

请按以下顺序输出：
1. 先概括代码的职责；
2. 按严重程度列出问题；
3. 对每个问题给出文件位置、原因、影响和修复建议；
4. 给出最小修改示例；
5. 列出仍需通过测试或人工确认的内容。

约束：
- 不要把风格偏好伪装成缺陷；
- 如果无法确认，请写出假设；
- 不要修改未提供的代码。

代码：
<<<
...
>>>
```

### 3. 信息提取模板

```text
请从下面的文本中提取结构化信息。

输出字段：
- name：名称；
- date：日期，统一为 YYYY-MM-DD；
- amount：金额，保留数字和币种；
- evidence：支持该字段的原文片段。

规则：
- 找不到字段时填写 null；
- 不要根据常识推断文本中没有出现的信息；
- 日期存在歧义时不要自行选择，放入 uncertainty 字段；
- 只输出 JSON。
```

### 4. 方案比较模板

```text
请比较【方案 A】、【方案 B】和【方案 C】。

背景：【项目背景、预算、时间和已有条件】
评价维度：成本、实施难度、维护成本、扩展性和主要风险。

输出：
1. 一张对比表；
2. 每个方案的适用场景；
3. 在当前背景下的推荐方案；
4. 如果背景中的某个条件改变，推荐是否会改变；
5. 需要我补充的关键信息。

不要只给出单一结论，要说明结论依赖的假设。
```

## 十三、从“会写提示词”进阶到“会设计 AI 工作流”

真正高效的 AI 使用方式，通常不是写一条越来越长的提示词，而是把任务拆成多个清晰的步骤：

```text
原始需求
   ↓
需求澄清
   ↓
资料整理与检索
   ↓
初稿生成
   ↓
规则检查
   ↓
人工确认
   ↓
最终交付
```

每一步都应该有明确输入和输出。例如：

- 需求澄清阶段输出目标、受众和边界；
- 资料整理阶段输出带来源的事实清单；
- 生成阶段只使用已经确认的资料；
- 检查阶段验证格式、长度、事实和敏感内容；
- 人工确认阶段负责最终决策和发布。

这样做比“让 AI 自己完成所有事情”更容易定位问题，也更适合团队协作和长期维护。

## 十四、最后的检查清单

每次提交一个重要提示词前，可以快速检查：

- [ ] 任务是否用一个明确的动作描述，例如总结、分类、比较或改写？
- [ ] 是否说明了目标读者、使用场景和必要背景？
- [ ] 输入资料和指令之间是否有清晰边界？
- [ ] 是否写明了长度、语言、语气和输出格式？
- [ ] 是否说明了信息不足时应该怎么处理？
- [ ] 是否提供了一个足够接近真实任务的示例？
- [ ] 是否把“不要做什么”改写成了可执行的替代行为？
- [ ] 输出是否需要经过 JSON、字段、长度或安全校验？
- [ ] 是否用正常、边界和异常样例测试过？
- [ ] 是否保留了人工审核和事实核查环节？

## 结语

好的提示词不是一段华丽的咒语，而是一份写给 AI 的清晰任务说明。它至少应该回答五个问题：**要做什么、依据什么、遵守什么规则、以什么格式交付、怎样判断合格。**

当你开始把提示词当成可测试、可复用、可维护的配置，而不是一次性的聊天话术，AI 才会从“偶尔给出惊喜的问答工具”，逐渐变成一个更稳定的协作助手。
